회사에서 "AI 에이전트 만들자"는 말이 나오면서, 나부터 환상을 좀 걷어내고 싶었다.
챗봇이랑 에이전트가 뭐가 다른 건지, 왜 프롬프트 길게 쓴다고 되는 게 아닌지, RAG는 대체 왜 쓰는 건지.
사람들이 자주 헷갈리는 지점만 골라서, 최대한 쉬운 비유로 정리해봤다.

결론부터 말하면 이렇다. **AI 에이전트 개발은 똑똑한 모델을 만드는 일이 아니라,
말 안 듣는 LLM을 데리고 일 시키려고 데이터 정리하고 비용 새는 거 막는 노가다다.**

## 1. 챗봇이랑 에이전트, 뭐가 다른데?

> 흔한 오해: 프롬프트 길게 쓰고 툴 몇 개 붙이면 에이전트다.

그건 그냥 **자판기**다. 동전 넣으면(질문) 음료수 하나 나오고(툴 한 번 호출) 끝.
질문 → 툴 실행 → 답변, 딱 한 줄로 흘러간다.

에이전트는 **알바생**에 가깝다. "이 택배 다 돌리고 와"라고 시키면,
주소 보고 → 갔다가 → 부재중이면 → 경비실 맡기고 → 다음 집 가고... 이걸 목표 끝날 때까지 알아서 반복한다.
`생각 → 행동 → 결과 확인 → 다시 생각`을 계속 돈다.

근데 알바생한테 "알아서 회사 살려놔" 수준으로 풀어주면 사고 친다.
어디서 왜 틀렸는지 추적도 안 된다. 그래서 현실적인 답은 **할 일을 좁게 정해준 알바생**이다.
"이 목록에 있는 집만, 이 동선으로" 정도로 자유도를 묶어놓고 돌리는 게 낫다.

## 2. LLM은 붕어다 (기억력 3초)

> 흔한 오해: 모델이 아까 한 대화를 기억하고 있다.

안 한다. LLM은 **매번 처음 보는 사람**이다.
어제 3시간 얘기했어도 오늘 다시 만나면 "누구세요?"부터 시작한다.

그럼 챗봇은 어떻게 대화가 이어지냐고? 간단하다.
**말 걸 때마다 지금까지 나눈 대화 전체랑 회사 규칙을 통째로 프린트해서 손에 쥐여주고 질문한다.**
"자, 여기 우리가 어제 나눈 얘기 전부 있고요, 회사 규칙집도 여기 있고요, 그래서 제 질문은..."
우리가 "기억하네?" 하는 건 착시고, 저 프린트물 값이 매번 청구된다.

### 규칙집을 매번 낭독하면 생기는 일

시스템 프롬프트든 `README.md`든 뭐든, API 부를 땐 전부 "질문 앞에 붙는 긴 글자 뭉치"로 바뀐다.

**1) 숨만 쉬어도 나가는 기본요금**

규칙집이 10,000토큰이면, "안녕"이라고만 쳐도 매번 10,000토큰이 청구된다.
5턴 대화하면 5번 다시 낭독한다. 대화가 길어질수록 눈덩이다.

**2) 정작 중요한 말은 흘려들음**

사람도 30분 브리핑 들으면 앞에 뭐라 했는지 까먹는다. LLM도 똑같다.
배경 설명이 수만 자면, "출력은 무조건 JSON", "DB는 읽기만" 같은 진짜 중요한 규칙이 글자 더미에 파묻혀서 무시된다.

**3) 도구 설명서까지 얹힘**

MCP 툴을 붙이면 툴 이름, 설명, 사용법도 전부 글자로 같이 들어간다.
규칙집 + 툴 설명서 잔뜩 = 질문 받기도 전에 수만 토큰 먹고 시작 → 응답이 눈에 띄게 느려진다.

### 그래서 현업은 이렇게 피한다

- **프롬프트 캐싱**: 안 바뀌는 앞부분(규칙집)을 서버에 복사해두고 매번 다시 안 읽는다.
  고정 토큰 비용을 75~90% 깎고 속도도 빨라진다. 규칙집 떡칠을 유지할 거면 이건 필수.
- **규칙집을 '서랍'에 넣기**: 시스템 프롬프트엔 핵심 3~5줄만 두고,
  `사내문서_검색(키워드)` 같은 조회 도구를 하나 쥐여준다. 필요할 때만 알아서 서랍 열어보게 한다.

## 3. RAG는 왜 쓰냐면

> 흔한 오해: RAG는 정확도 올리려는 고급 기술이다.

아니다. RAG가 표준이 된 진짜 이유는 **돈이 안 나가게 하려고**다.

- 규칙집 떡칠: 시험장에 백과사전 10권 짊어지고 들어가기
- RAG: 일단 몸만 들어가고, 1번 문제 보고 필요한 페이지 2장만 찢어서 갖다주기

사내 문서가 A4 500장(약 30만 토큰)이라고 치면:

| 구분 | 규칙집 떡칠 | RAG |
| --- | --- | --- |
| 방식 | 질문마다 30만 토큰 통째로 전송 | 관련 단락 2~3개(약 1,000토큰)만 전송 |
| 입력 토큰 | 약 300,100 | 약 1,100 |
| 비용 | 질문당 수백~수천 원 | 질문당 몇 원 |
| 속도 | 30만 자 매번 정독 → 느림 | 1,000자만 읽음 → 즉시 |
| 정확도 | 볼 게 너무 많아 엉뚱한 거 참조 | 관련 페이지만 봐서 정확 |

### RAG의 성패는 모델이 아니라 "밑반찬 손질"

> 흔한 오해: RAG 만든다 = 프롬프트 잘 짠다.

아니다. 8~90%는 **문서를 어떻게 잘라서(청킹) 어떻게 담아뒀냐(인덱싱)**에서 갈린다.
현업에서 "RAG 만든다"며 시간 쏟는 곳은 화려한 프롬프트가 아니라,
지저분한 문서 파싱하고 잘라서 DB에 밀어 넣는 **주방 밑작업**이다.

검색기(Vector DB)는 생각보다 멍청하다. 글 전체를 이해하는 게 아니라,
내가 썰어놓은 **조각 단위로만** 비슷한 걸 찾는다.

- **써는 크기 조절**: 너무 잘게 썰면(100자) 정확한데 앞뒤 맥락이 날아가서 헛소리를 한다.
  너무 크게 썰면(2,000자) 맥락은 있는데 잡내가 섞여서 엉뚱한 걸 집어온다.
  잘하는 사람은 문단, 마크다운 헤더, 코드 블록 단위로 맥락 안 깨지게 썬다.
- **포맷 지옥**: 회사 문서는 깨진 한글 PDF, 셀 병합 떡칠된 엑셀, PPT 그림이다.
  표를 그냥 글자로 긁으면 행·열이 다 엉킨다. 표는 표 모양(Markdown/HTML)으로 살려서 넣어야 한다.
- **검색 섞어 쓰기**: 의미 검색은 "서버 터졌을 때 어떡해?" 같은 뉘앙스는 잘 찾는데
  `NullPointerException`, `ORD_2026_09` 같은 정확한 단어엔 약하다. 키워드 검색은 그 반대다. 둘을 섞는다.

### 청킹이 중요한 이유: 믹서기에 다 갈면 무슨 맛인지 모른다

> 흔한 오해: 지라 티켓 하나를 통째로 넣어야 맥락이 살아서 정확하다.

임베딩 모델은 글을 읽고 **숫자 배열 하나로 압축**한다(예: 1536칸).

- 딸기만 갈면 → 딸기맛 (뚜렷함)
- 딸기 + 밥 + 김치 + 커피를 같이 갈면 → 정체불명의 갈색 액체 (**희석**)

지라 티켓 하나엔 보통 이게 다 섞여 있다.

1. 증상: "결제창에서 500 에러"
2. 원인: "Redis 세션 타임아웃 설정 누락"
3. 댓글 20개: "확인 부탁드려요", "배포 언제 되나요?", "로그 첨부합니다"
4. 해결: "타임아웃 3초로 바꾸니 됨"

이걸 통째로 갈아버리면 그 숫자 배열은 'Redis 문제'가 아니라
"결제, 에러, 일정 얘기, 인사말이 다 섞인 갈색 액체"를 가리킨다.
나중에 누가 "Redis 타임아웃 에러"로 검색하면 댓글 잡내에 밀려서 못 찾는다.

의미 단위로 썰면 이렇게 된다.

```
조각 A [증상]      : "결제창 500 에러, 로그 스택트레이스"
조각 B [원인/해결] : "Redis 세션 타임아웃 3초 수정으로 해결"
(버림) [댓글 잡담] : "회의 언제 할까요?" → 아예 안 넣음
```

"결제 500 에러"로 찾으면 조각 A가, "Redis 세션 해결법"으로 찾으면 조각 B가 딱 걸린다.

**전체 맥락이 필요하면?** 검색은 잘게 썬 조각으로 하고,
하나라도 걸리면 그 조각이 들어있던 **원본 티켓 전체**를 꺼내서 LLM한테 준다.
찾을 땐 뾰족하게, 읽을 땐 넉넉하게(Small-to-Big).

**목적이 "예전에 비슷한 장애 있었나 찾기"뿐이면** 해결책이나 댓글은 넣을 이유가 없다.
증상(조각 A)만 발라서 넣는 게 정확도도, 비용도, 구조도 다 낫다.
지라 API에서 `제목 + 증상 본문`만 긁어서 한 조각으로 묶으면 끝.

### 벡터 vs 메타데이터: 택배 상자 비유

> 흔한 오해: 메타데이터(JSON)도 같이 임베딩하면 꺼낼 때 같이 나온다.

**메타데이터는 임베딩 안 한다.** 순수 텍스트만 갈고, 나머지 정보는 그냥 옆에 붙여둔다.

```
[ Vector DB 레코드 1개 ]
├── 1. 벡터(숫자 좌표): [0.024, -0.115, 0.884, ...]   <- "증상 텍스트"만 갈아서 만든 것
└── 2. 메타데이터(그냥 JSON):                          <- 안 갈고 원본 그대로 저장
      {
        "jira_key": "PROJ-1024",
        "jira_url": "https://jira.company.com/browse/PROJ-1024",
        "created_at": "2026-03-15",
        "assignee": "김개발",
        "status": "Resolved"
      }
```

택배 상자로 보면 —
**벡터는 상자 겉면 바코드**다. 컴퓨터는 이 바코드만 찍어서 상자를 찾는다.
**메타데이터는 상자 안에 든 물건들**이다(티켓 링크, 날짜, 담당자, 원문).
바코드로 상자를 딱 찾으면, 안에 담아둔 게 통째로 딸려 나온다.

JSON을 통째로 갈아버리면 `jira_key`, 따옴표, 중괄호, 날짜 같은 게 벡터 계산에 섞여서
또 갈색 액체가 된다. "결제창 에러"라는 원래 의미가 흐려진다.

메타데이터를 안 갈고 옆에 들고 있으면 **먼저 거르기(Pre-filtering)**가 된다. 도서관에서
"2020년 이후 요리책 코너"로 먼저 걸어간 다음 그 안에서 찾는 것처럼.

- "2025년 이후 티켓 중에서만 비슷한 거 찾아줘"
- "결제 모듈 티켓 중에서만 찾아줘"

범위를 먼저 좁히고 그 안에서만 비교하니까 속도랑 정확도가 확 오른다.

실제 동작은 이렇게 단순해진다.

1. 새 에러가 들어옴 → 증상 텍스트로 검색
2. 제일 비슷한 옛날 조각 1~3개가 나옴
3. 메타데이터에서 티켓 링크 꺼내서 바로 던져줌
   → "작년 3월 김개발 님이 처리한 PROJ-1024랑 증상 92% 똑같아요. [티켓 바로가기]"

## 4. "생각하는 시간"도 돈이다

> 흔한 오해: 컨텍스트 넘기고 모델이 생각하는 동안은 공짜다.

모델 종류에 따라 다르다.

- **일반 모델 (Claude Sonnet, GPT-4o 등)**: 답 나올 때까지 뜸 들이는 시간은 있어도 공짜다.
  넣은 토큰 + 뱉은 토큰만 계산한다. 3초 걸리든 10초 걸리든 그 사이 계산은 무료.
- **추론 모델 (o1/o3, Gemini Thinking 등)**: 답을 바로 안 하고 **혼잣말로 한참 생각을 적는다.**
  그 혼잣말 분량이 전부 토큰으로 청구된다. 화면엔 가려져 보여도 요금은 그대로 나가고,
  단가도 보통 일반 출력보다 2~4배 비싸다.

그래서 지라 티켓 검색 같은 단순 작업에 추론 모델 붙이면 "혼잣말 = 실시간 요금 폭탄 + 느려터짐"이 된다.
큰 흐름 관리나 툴 호출은 가벼운 모델로 하고, 진짜 어려운 논리나 디버깅이 필요한 한두 단계만 추론 모델을 쓴다.

## 5. 우리 팀이 당장 할 것

**1단계 — 문서 얼마 없으면 (A4 10~20장):**
RAG 만들지 말고 **프롬프트 캐싱** 켜고 그냥 통째로 넣기. 개발 속도가 압도적으로 빠르다.

**2단계 — 목적 뚜렷한 가벼운 RAG:**
"과거 장애/문의 찾기"처럼 목적이 분명한 것부터. **증상 텍스트만 임베딩 + 메타데이터(링크·담당자·날짜) 붙이기.**
`제목 + 본문`을 한 조각으로 묶고, 나머지는 필터용 메타데이터로.

**3단계 — 단일 목적 워크플로우 툴:**
검색 결과 갖고 슬랙 알림 쏘거나 지라 티켓 만드는 정도의 1~2단계짜리. 자유도 좁게 묶어놓고 시작.

## 한 줄 요약

- 에이전트는 자판기가 아니라 알바생이다. 근데 할 일 좁게 정해준 알바생이 낫다.
- LLM은 붕어다. "기억"은 매번 대화 전체를 프린트해서 쥐여주는 거고, 그 값이 청구된다.
- 규칙집 매번 낭독하면 기본요금 나가고, 중요한 말은 파묻히고, 응답 느려진다. → 캐싱하거나 서랍에 넣기.
- RAG는 정확도보다 **돈** 때문에 쓴다. 성패는 밑반찬 손질(청킹)에서 갈린다.
- 벡터는 상자 바코드(텍스트만), 메타데이터는 상자 속 물건(JSON). 같이 갈면 안 된다.
- 추론 모델의 혼잣말도 토큰이다. 큰 흐름은 가벼운 모델, 어려운 데만 추론 모델.
