         HTTP 1.1 : 연결은 재사용하지만 요청은 하나씩

         ```mermaid
         sequenceDiagram
             participant C as 클라이언트
             participant S as 서버
             Note over C,S: TCP 연결 1개 (keep-alive)
             C->>S: GET /a.css
             S-->>C: a.css
             C->>S: GET /b.js
             S-->>C: b.js
             Note over C,S: 앞 요청이 끝나야 다음 요청 (HOL blocking)<br/>그래서 브라우저는 연결을 6개 정도 병렬로 열었다
         ```

         HTTP 2.0 : 연결 하나에 스트림 여러 개 (멀티플렉싱)

         ```mermaid
         sequenceDiagram
             participant C as 클라이언트
             participant S as 서버
             Note over C,S: TCP 연결 1개, 스트림 여러 개
             C->>S: 스트림1 GET /a.css
             C->>S: 스트림3 GET /b.js
             S-->>C: 스트림3 b.js
             S-->>C: 스트림1 a.css
             Note over C,S: 응답 순서 상관없이 동시에 진행, 헤더 압축(HPACK)<br/>하지만 TCP 패킷 하나가 유실되면 모든 스트림이 같이 멈춘다
         ```

         HTTP 3.0 : TCP 대신 QUIC(UDP 위), 스트림이 서로 독립

         ```mermaid
         sequenceDiagram
             participant C as 클라이언트
             participant S as 서버
             Note over C,S: QUIC 연결 1개 (UDP), TLS 1.3 내장
             C->>S: 핸드셰이크 (연결 + TLS 를 한 번에)
             S-->>C: 핸드셰이크 응답
             C->>S: 스트림1 GET /a.css
             C->>S: 스트림3 GET /b.js
             S-->>C: 스트림3 b.js
             S-->>C: 스트림1 a.css
             Note over C,S: 패킷이 유실돼도 해당 스트림만 재전송, 나머지는 계속 진행<br/>연결 ID 로 식별해서 와이파이에서 LTE 로 바뀌어도 연결 유지
         ```

3. 기초: 질문으로 배우는 컴퓨터
   - Q1. `python script.py` 를 치면 컴퓨터 안에서 무슨 일이 일어날까? <!-- 프로세스 1개 + 스레드 1개가 만들어지고 코어 하나를 쓴다. 기다릴 때는 쉬고, 경쟁이 있을 때만 교대한다 -->
     - CPU 코어, 메모리 <!-- 코어는 한 순간에 하나의 명령만 실행. 메모리는 스택 / 힙 -->
     - 프로세스 vs 스레드 <!-- 프로세스는 메모리가 따로, 같은 프로세스의 스레드끼리는 메모리를 공유 (스택만 따로) -->
   - Q2. 내가 짠 코드를 CPU 는 어떻게 알아들을까? <!-- CPU 는 기계어(0과 1)만 읽는다. 파이썬 소스는 실행할 때 바이트코드로 컴파일되고, 기계어로 된 C 프로그램(CPython, 흔히 PVM)이 그 바이트코드를 한 줄씩 읽어 실행한다 -->
     - 번역 사다리 (PVM) <!-- 소스 -> 바이트코드 -> PVM(C 로 짠 프로그램) -> 기계어 -> 트랜지스터(플립플롭). 한 줄이 수십 개의 기계어 명령이 되어서 상대적으로 느리다 -->
       - GIL(Global Interpreter Lock)
         - 참조카운트와 순환 GC
     - ISA <!-- CPU 와 소프트웨어 사이의 계약서(명령어 집합). x86(인텔, AMD), ARM(애플, 퀄컴, AWS Graviton), RISC-V(오픈). 같은 ISA 면 내부 회로가 달라도 같은 기계어가 돈다. 설명은 짧게 -->
     - C 코드 -> 어셈블리 (컴파일 결과) <!-- 같은 C 코드도 ISA 가 다르면 기계어가 다르다. 인자 레지스터가 x86 은 edi/esi, ARM 은 w0/w1. 각 줄의 주소가 프로그램 카운터, rsp/sp 가 스택 포인터 -->

       <details markdown="1">
         <summary>같은 C 코드를 x86_64 와 arm64 로 컴파일하면</summary>

         ```c
         int add(int a, int b) { int sum = a + b; return sum; }
         void main_like() { result = add(3, 4); }
         ```

         | | x86_64 | arm64 |
         |---|---|---|
         | 인자 3, 4 넣기 | `movl $3, %edi` / `movl $4, %esi` | `mov w0, #3` / `mov w1, #4` |
         | 함수 호출 | `callq _add` | `bl _add` |
         | 더하기 | `addl -8(%rbp), %eax` | `add w8, w8, w9` |
         | 스택 준비 / 정리 | `pushq %rbp` / `popq %rbp` | `sub sp, sp, #16` / `add sp, sp, #16` |

       </details>
     - 컴파일 vs 인터프리트 <!-- C 는 한 번에 기계어(VM 없음, 플랫폼마다 다시 빌드). Java 와 Python 은 바이트코드로 컴파일한 뒤 VM 이 실행 -->
   - Q3. 코어는 4개인데 스레드가 50개면 누가 먼저 CPU 를 쓸까?
     - 시분할 처리와 컨텍스트 스위칭 <!-- 몇 ms 단위(타임 슬라이스)로 번갈아 CPU 를 쓴다. 경쟁이 있을 때만 일어난다. 쫓겨날 때 프로그램 카운터(Q2 어셈블리의 줄 주소)와 레지스터(스택 포인터 포함)만 TCB 에 저장, 데이터는 메모리에 그대로. 전환 자체는 수 마이크로초, 진짜 비용은 캐시/TLB 가 식는 것. 프로세스 전환이 더 무거운 이유는 주소 공간이 바뀌기 때문. TCB 는 커널 메모리에 있다 -->
       - 가중치 기반 업무배정 <!-- 리눅스 스케줄러(CFS, EEVDF)는 스레드마다 가중치를 두고 비율대로 CPU 시간을 나눠 준다. nice 값이 가중치 -->
     - 내 프로그램만 우선순위를 높일 수 있을까? <!-- nice 는 낮추는 건 자유, 높이는 건 권한 필요. 실시간 스케줄링도 root 가 필요하고 RT throttling 이 있다. 높은 우선순위끼리 우선순위 역전, 기아 -->
     - 노래, 게임, 커널UX 쓰레드 동시에 처리하는 CPU <!-- 노래 재생은 마감 시간이 있는 작업(버퍼를 제때 못 채우면 끊김)이라 평소엔 자다가 주기적으로 깨는 높은 우선순위 스레드. 게임은 16.6ms 프레임 안에 입력, 로직, 그리기를 끝내야 해서 역할별 스레드와 잡 시스템 -->
     - 커널(OS) & 준비큐 & 대기큐 <!-- 커널은 RAM 에 상주하며 스레드를 스케줄링한다. 준비 큐는 CPU 만 받으면 바로 달릴 수 있는 스레드가 줄 서는 곳, 대기 큐는 I/O 완료나 락 같은 사건을 기다리는 스레드가 잠들어 있는 곳(사건마다 따로 있다). 요즘 OS 는 코어마다 큐가 따로 있다. 상태 흐름은 준비 -> 실행 -> 대기 -> 준비 -->
   - Q4. 내 코드가 파일이나 네트워크를 읽으려 하면 커널은 무슨 일을 할까?
     - 시스템 콜 <!-- 파일, 네트워크는 내 코드가 직접 못 만지고 커널에게 부탁한다. 유저 모드 -> 커널 모드 전환 -->
       - 프로그램과 커널 전용창구 (read, socket, epoll)
     - CPU 위주 작업 vs I/O 위주 작업 <!-- 계산 vs DB / 네트워크 / 디스크 대기. 서버는 대부분 I/O 대기 -->
     - epoll, socket, port, NIC 카드 <!-- 소켓은 통신 끝점(커널 객체, fd), 포트는 패킷이 어느 소켓으로 갈지 정하는 헤더의 숫자, NIC 는 패킷을 신호로 바꾸는 물리 장치. 일을 맡기고 알림(콜백)을 기다린다고 생각하면 된다. 블로킹 read(스레드가 대기 큐에서 잠들고 데이터가 도착하면 인터럽트가 깨워서 준비 큐로), 논블로킹 read(바로 돌아옴, polling), epoll(준비 알림, 이벤트루프의 기반), io_uring(완료 알림) -->
       - NIC -> 포트 -> 소켓찾기 -> 소켓데이터읽는큐 깨움 -> 준비큐 -> 실행
       - 내 코드 -> 소켓에 데이터 쌓기 -> 소켓에 배정된 포트 +상대포트 -> NIC드라이버 -> 케이블
   - Q5. 서버는 요청을 어떻게 나눠서 처리할까? <!-- 찍먹만 하고 자세한 건 세부 전공에서 -->

6. 인증
   - OAuth 2.0
   - 가장 일반적인 AUTH_CODE 방식 다이어그램
     ```mermaid
     sequenceDiagram
         participant B as 브라우저 (사용자)
         participant S as 내 백엔드 서버
         participant O as OAuth 인증 서버 (구글/카카오)

         Note over B,O: 1단계 인증
         B->>O: 1. ID / PW 전송 (HTTPS)
         Note right of O: 신원 검증, 동의 확인
         O-->>B: 2. 302 Redirect (callback?code=AUTH_CODE)

         Note over B,S: 2단계 코드 전달
         B->>S: 3. GET /callback?code=AUTH_CODE

         Note over S,O: 3단계 토큰 교환
         S->>O: 4. POST /token (code + Secret Key)
         Note right of O: code, Secret 검증
         O-->>S: 5. Access Token 응답

         Note over S: 4단계 자체 JWT<br/>사용자 정보 조회 & 회원가입<br/>자체 서비스용 JWT 발급

         Note over B,S: 5단계 정착
         S-->>B: 6. 최종 응답<br/>(A: Set-Cookie 에 JWT / B: JSON 본문에 JWT)
     ```
