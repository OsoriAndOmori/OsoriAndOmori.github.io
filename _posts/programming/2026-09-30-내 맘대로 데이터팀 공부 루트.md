1. 파이썬 런타임과 동시성
   - 코루틴 <!-- 중간에 멈췄다가 이어서 실행할 수 있는 함수 (async / await) -->
   - 2 x 2 예시 <!-- boto3 호출, await, 콜백 등은 어디에 들어가는지 채워보기 -->
   - 이벤트루프 막힘 <!-- 동기(블로킹) 코드가 이벤트루프를 막으면 다른 일이 전부 멈춘다 -->
   - GIL
     - 한 프로세스에서 한 스레드만 <!-- 파이썬 코드는 한 번에 한 스레드만 실행한다 -->
     - I/O 대기 중 GIL 해제 <!-- 그래서 스레드가 I/O 에는 의미가 있다 -->
     - CPU 는 프로세스로 <!-- CPU 를 여러 코어로 쓰려면 프로세스를 나눈다 -->
   - 실습) 스레드 / 프로세스 / asyncio 로 CPU 작업, I/O 작업 시간 비교

2. 서버를 직접 만들며 배우기 : WSGI -> ASGI -> FastAPI
   - 2-1. WSGI 서버 만들기 (스레드풀)
     - 단일 스레드 서버 <!-- 소켓으로 accept → 처리 → 응답 반복. 처리 안에서 time.sleep(5)(또는 boto3 호출)을 넣고 요청 2개를 동시에 보내면 두 번째는 못 받고 기다린다 -->
     - 스레드풀 붙이기 <!-- accept 한 연결을 빈 스레드에 던진다 (Tomcat 방식). 문제는 def 라는 문법이 아니라 그 코드를 어느 스레드가 실행하느냐 -->
     - WSGI 인터페이스 <!-- app(environ, start_response). 서버가 요청을 파싱해서 앱 함수를 부르는 약속. Django, Flask 는 이 약속을 지키는 앱이고 gunicorn 이 서버 -->
     - 스레드 고갈 체험 <!-- 스레드풀 2개, 핸들러 안에서 sleep 5, 브라우저 탭 3개를 동시에 새로고침 → 세 번째는 앞의 둘이 끝날 때까지 멈춘다 -->
     - 스레드를 무한정 늘리면 안 될까? <!-- 스레드마다 스택 메모리(가상 메모리 기준 수 MB), 컨텍스트 스위칭 비용, GIL. 그래서 다른 방법이 필요하다는 문제의식을 만든다 -->
   - 2-2. ASGI 서버 만들기 (이벤트루프)
     - select 로 미니 이벤트루프 <!-- selectors 로 소켓 여러 개를 한 스레드가 번갈아 처리. 스레드를 늘리지 않았는데 요청을 놓치지 않는 이유. 커널의 epoll 이 기반 -->
     - asyncio 로 전환 <!-- 콜백 대신 async / await. 핸들러 안에서 time.sleep 과 await asyncio.sleep 을 바꿔가며 동시 요청 처리량 비교 -->
     - ASGI 인터페이스 <!-- app(scope, receive, send). 비동기 소켓 서버가 HTTP 를 파싱해서 앱을 부르는 약속. uvicorn 이 서버 역할 -->
     - 직접 만든 앱을 진짜 uvicorn 으로 띄워보기 <!-- 규격을 지켰으니 그대로 뜬다 -->
     - 이벤트루프 막힘 체험 <!-- 핸들러 안에 time.sleep(3) → 동시 curl 3개가 9초. asyncio.sleep 으로 바꾸면 3초 -->
   - 2-3. FastAPI 보기
     - 미니 라우터 `@app.get` <!-- scope["path"] 로 핸들러를 찾아 실행하는 Starlette 의 역할 -->
     - 타입 힌트로 파라미터 주입 <!-- inspect.signature 로 함수 시그니처를 읽어 자동 변환. FastAPI 의 마법의 정체 -->
     - 진짜 FastAPI 로 바꿔보기 <!-- 우리가 만든 조각들이 FastAPI 안에서 어디에 대응하는지 찾아보기 -->
     - `def` vs `async def`
       - `async def` <!-- 이벤트루프에서 직접 실행 -->
       - `def` <!-- 스레드풀에서 실행 -->
       - `async def` 안의 동기 코드 <!-- time.sleep, requests, boto3 를 부르면 서버 전체가 멈춘다 -->
       - boto3 <!-- 동기(블로킹) 라이브러리. FastAPI 가 비동기로 바꿔주는 게 아니라, def 로 쓰면 스레드풀에서 돌려줘서 다른 요청을 막지 않을 뿐 -->
       - 스레드풀 크기 <!-- 호출 자체는 여전히 블로킹이고, 동시 처리 상한은 스레드풀 크기(기본 40). Tomcat 워커 스레드풀과 비슷하지만 async def 는 이벤트루프 스레드에서 돈다 -->
     - 실습) boto3(localstack S3) 호출을 `async def` / `def` 로 만들고 동시 요청 10개 시간 비교
     - 멀티프로세스
       - `uvicorn --workers N` <!-- 프로세스가 N개, 각자 이벤트루프 + 스레드풀을 따로 가진다 -->
       - 실습) 응답에 PID 찍어서 분산 확인
   - 2-4. 용도에 맞게 서버 고르기 (마무리)
     - 성능 차이의 본질 <!-- I/O 대기 시간에 서버 자원을 얼마나 재사용하느냐. 처리량(동시에 붙들 수 있는 연결 수)의 차이이고, 응답이 아주 짧은 요청에서는 차이가 작다 -->
     - ASGI 가 맞는 경우 <!-- WebSocket, SSE, LLM 스트리밍처럼 연결을 오래 잡는 서비스. 외부 API 를 병렬로 호출해 조합하는 게이트웨이. 적은 서버로 많은 연결 -->
     - WSGI 로 충분한 경우 <!-- 전통적인 CRUD, 사내 관리 도구. 동기 라이브러리(boto3 등)에 많이 의존하는 경우. 팀의 비동기 숙련도 -->
     - ASGI 에서 블로킹 호출은 장애 <!-- 이벤트루프가 멈춰서 모든 요청이 같이 멈춘다 -->
     - 우리 팀 서비스에는 무엇이 맞을까? <!-- 마무리 토론. boto3 중심이라면? -->
   - 더 알아보면 좋은 것 : `asyncio.to_thread`, `aioboto3`, boto3 커넥션 풀(`max_pool_connections`), fork 이슈

3. 공통편에 얹히는 파이썬 항목
   - DB
     - 커넥션 풀 크기 산정 : 워커 수 x 풀 크기 <= DB max connections
   - 캐시와 타임아웃
     - 로컬 캐시 (`functools.lru_cache`, `cachetools`)
       - 멀티 프로세스에서 로컬 캐시의 함정
     - 각 구간 타임아웃 : httpx / boto3 / DB / uvicorn / LB
     - `asyncio.timeout` 과 취소 전파 (스레드로 넘어간 블로킹 호출은 취소가 안 된다!)
   - Web / 배포
     - uvicorn 을 직접 노출하면 안 되는 이유
     - Docker : 컨테이너 CPU 제한과 워커 수
       - 컨테이너 안 `os.cpu_count()` 함정
   - 로깅 / 모니터링
     - `logging` 설정, 구조화 로그(JSON), request-id 전파 (`contextvars` — 이벤트루프에서도 안전한 이유)
     - prometheus-client / OpenTelemetry + grafana
       - 꼭 볼 지표 : 이벤트루프 lag, 스레드풀 사용량, 워커별 RSS, boto3 커넥션 풀 대기
       - 일부러 스레드풀 소진 / 루프 막기 → 대시보드에서 관찰
     - 프로파일링 : `py-spy` (실행 중 프로세스 덤프), `tracemalloc`, memray
   - 테스트
     - pytest, fixture, parametrize
     - `moto` / `localstack` 로 AWS mock, `pytest-asyncio` / `anyio`
     - 테스트 데이터는 별도 factory 로 (`polyfactory` 등)
     - "mock 이 성공했는데 운영에서 터지는" 경험 : 왜 통합 테스트도 필요한가
   - 성능 테스트
     - 2번에서 만든 서버로 "병목이 어디인지" 맞추기
       - 이벤트루프? 스레드풀? 워커 수? DB 풀?
   - 아키텍처 설계
     - 우리 스택(FastAPI 워커 수 x 스레드풀, DB 커넥션 풀)으로 동시 요청을 몇 개까지 받을 수 있는지 계산해보기
   - 코딩 스킬
     - 파이썬스러움 (comprehension, generator, context manager) vs 과한 마법
     - 매일 15분 정도 표준 라이브러리 / FastAPI / Starlette 코드 읽기
