3. 기초: 내 코드는 어떻게 실행되나 (아래에서 위로 쌓아가기)
- 3-1. 하드웨어와 OS : 코드가 실행되는 바닥
  - CPU 코어 : 한 순간에 하나의 명령만 실행한다
  - 메모리 : 스택 / 힙
  - 프로세스 : 실행 중인 프로그램, 메모리 공간이 프로세스마다 따로 (서로 공유 안 됨)
  - 스레드 : 프로세스 안의 실행 흐름, 같은 프로세스의 스레드끼리는 메모리를 공유한다
  - 코어보다 스레드가 많으면? 번갈아 태운다 (컨텍스트 스위칭)
  - 동시성 vs 병렬성 : 번갈아 하는 것 vs 진짜 같이 하는 것
- 3-2. 문제는 "기다림" : 서버 코드의 시간은 대부분 어디서 쓰이나
  - CPU 바운드 vs I/O 바운드 (계산 vs DB / 네트워크 / 디스크 대기)
  - I/O 대기 중에 스레드는 뭘 하나? 그냥 잠들어 있다 → 아깝다
- 3-3. 용어 정리 : 두 개의 축
  - 블로킹 vs 논블로킹 : 호출한 스레드가 기다리는 동안 **멈추는가**
  - 동기 vs 비동기 : 결과를 **호출한 쪽이 직접 기다려 받는가**, 나중에 알려주는가
  - 2 x 2 로 예시 채워보기 (boto3 호출, `await`, 콜백 등은 어디에?)
- 3-4. 기다리는 시간을 활용하는 3가지 방법
  - 프로세스를 늘린다 : 메모리 따로, 무겁고 격리됨
  - 스레드를 늘린다 : 기다리는 스레드를 여러 개 (Tomcat 스타일)
  - 이벤트루프 : 스레드 하나로 기다리는 일을 번갈아 처리 (Node.js 와 같은 모델)
    - 코루틴 : 중간에 멈췄다가 이어서 실행할 수 있는 함수 (`async` / `await`)
    - 동기(블로킹) 코드가 이벤트루프를 막으면 다른 일이 전부 멈춘다
  - 비교표 직접 채워보기 : 메모리 / 생성 비용 / 동시 처리 수 / 함정
- 3-5. 파이썬만의 사정 : GIL
  - 한 프로세스에서 파이썬 코드는 한 번에 한 스레드만 실행한다
  - I/O 대기 중에는 GIL 이 풀리므로 스레드가 I/O 에는 의미가 있다
  - CPU 를 여러 코어로 쓰려면 프로세스를 나눈다
- 실습) 같은 작업을 스레드 / 프로세스 / asyncio 로 돌려서 CPU 작업, I/O 작업 시간 비교

4. FastAPI 와 동기/비동기 (실습 한 번으로 끝)
- 원시적인 서버 먼저 만들어보기 (FastAPI 없이)
  - 소켓으로 `accept` → 처리 → 응답을 반복하는 **단일 스레드 서버**
  - 처리 안에서 boto3 호출(또는 `time.sleep(2)`)하고 요청 2개를 동시에 보내보기 → 두 번째는 못 받고 기다린다
  - 스레드풀을 붙여보기 → 다른 스레드가 다음 요청을 받는다 (Tomcat 방식)
  - 요점 : 문제는 `def` 라는 문법이 아니라 **그 코드를 어느 스레드가 실행하느냐**
- **`def` vs `async def`** ⭐ 이것만은 가져가기
  - `async def` → 이벤트루프에서 직접 실행, `def` → 스레드풀에서 실행
  - `async def` 안에서 동기 코드(`time.sleep`, `requests`, **boto3**)를 부르면 서버 전체가 멈춘다
  - boto3 는 동기(블로킹) 라이브러리다. FastAPI 가 비동기로 바꿔주는 게 아니라, `def` 로 쓰면 스레드풀에서 돌려줘서 **다른 요청을 막지 않을 뿐**이다
  - 호출 자체는 여전히 블로킹이고, 동시 처리 상한은 스레드풀 크기(기본 40)
  - Tomcat 워커 스레드풀과 비슷한 느낌 (요청 하나 = 스레드 하나). 다만 `async def` 는 스레드풀이 아니라 이벤트루프 스레드에서 돈다는 점이 다르다
  - 그래서 "async 붙이면 빨라진다" 는 오해
- 실습) 같은 boto3(localstack S3) 호출을 `async def` / `def` 두 가지로 만들고 동시 요청 10개 던져서 시간 비교
- 멀티프로세스는 개념만 : uvicorn `--workers N` 하면 프로세스가 N개, 각자 이벤트루프 + 스레드풀을 따로 가진다
  - 실습) 응답에 PID 찍어서 분산되는 것만 확인
- 나중에 더 파볼 것 (지금은 이름만 알아두기) : `asyncio.to_thread`, `aioboto3`, boto3 커넥션 풀(`max_pool_connections`), fork 이슈

8. Web / Proxy / 배포
- 리버스 프록시(nginx / ALB), uvicorn 을 직접 노출하면 안 되는 이유
- Docker : 이미지 만들기, 멀티스테이지, 컨테이너 CPU 제한과 워커 수
  - 컨테이너 안 `os.cpu_count()` 함정
- 배포 방식의 진화
  - 고전적인 Jenkins 배포 : 빌드 → 산출물 전송(scp / rsync) → SSH 로 접속해서 배포 명령 (push 방식)
    - Jenkins 서버가 대상 서버의 SSH 키(Credentials)를 들고 있다
    - 문제점 : 키 유출 위험, 서버가 많으면 느리고 버전이 어긋날 수 있음, 롤백을 직접 스크립트로
  - Ansible : 여러 서버에 같은 작업을 반복 (플레이북)
  - 컨테이너 / k8s / GitOps : 이미지를 배포 단위로, 서버가 가져가는 pull 방식
- 배포 전략 rolling / blue-green / canary, Health check, graceful shutdown
- 실제 2대(or 컨테이너 2개)로 무중단 배포 해보기
- 시간 남으면 k8s
