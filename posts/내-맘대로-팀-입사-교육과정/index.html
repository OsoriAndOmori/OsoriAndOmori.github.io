  1. 문화와 성장
    • 모르는건 동료 개발자에게 바로 물어봐야할까?
      • 팀 자체에 심리적 안정감이 있는가?
    • 동료와 개발 의견이 다를땐 어떻게 해야하나.. 저도 아직 잘 모르겠음.
      • 코딩 스타일의 차이
      • 설계 차이
    • 계몽 vs 전염 뭐가 더 좋은가
    • 개발자의 역할은 뭘까
      • 요구되는 비즈니스 구현 vs 기술부채 해결하며 안정적이고 우아한 시스템 구현
    • 좋은 성과를 내는 개발자와 평가
      • 맨날 하던 방식, 기존의 틀 깨기
      • 시킨 일은 기본, 남는 시간에 한 걸음 더 가기
      • 현재 직급보다 한 단계 위의 일을 미리 해보기 (신입은 대리급, 대리는 과장급)
    • 기술적으로 빠른 성장방법
      • 학자형 vs 야생형
      • CS 지식들 업무에 녹이기
        • 40% 정도는 알고 있는 일을 새로 배우기
    • 어디서든 쓰는 기본 기술에 투자하기
      • 특정 팀의 도구보다 어디서든 통하는 기본기
      • 개인에게 좋은 일 vs 팀에게 좋은 일
    • 자기 객관화 도구
      • 이력서 관리와 도전들

      • 버전별 비교 (1.1 / 2.0 / 3.0)

        다이어그램 펼치기

        HTTP 1.1 : 연결은 재사용하지만 요청은 하나씩

          sequenceDiagram
      participant C as 클라이언트
      participant S as 서버
      Note over C,S: TCP 연결 1개 (keep-alive)
      C->>S: GET /a.css
      S-->>C: a.css
      C->>S: GET /b.js
      S-->>C: b.js
      Note over C,S: 앞 요청이 끝나야 다음 요청 (HOL blocking)<br/>그래서 브라우저는 연결을 6개 정도 병렬로 열었다

        HTTP 2.0 : 연결 하나에 스트림 여러 개 (멀티플렉싱)

          sequenceDiagram
      participant C as 클라이언트
      participant S as 서버
      Note over C,S: TCP 연결 1개, 스트림 여러 개
      C->>S: 스트림1 GET /a.css
      C->>S: 스트림3 GET /b.js
      S-->>C: 스트림3 b.js
      S-->>C: 스트림1 a.css
      Note over C,S: 응답 순서 상관없이 동시에 진행, 헤더 압축(HPACK)<br/>하지만 TCP 패킷 하나가 유실되면 모든 스트림이 같이 멈춘다

        HTTP 3.0 : TCP 대신 QUIC(UDP 위), 스트림이 서로 독립

          sequenceDiagram
      participant C as 클라이언트
      participant S as 서버
      Note over C,S: QUIC 연결 1개 (UDP), TLS 1.3 내장
      C->>S: 핸드셰이크 (연결 + TLS 를 한 번에)
      S-->>C: 핸드셰이크 응답
      C->>S: 스트림1 GET /a.css
      C->>S: 스트림3 GET /b.js
      S-->>C: 스트림3 b.js
      S-->>C: 스트림1 a.css
      Note over C,S: 패킷이 유실돼도 해당 스트림만 재전송, 나머지는 계속 진행<br/>연결 ID 로 식별해서 와이파이에서 LTE 로 바뀌어도 연결 유지

  6. 인증
    • OAuth 2.0
    • 가장 일반적인 AUTH_CODE 방식 다이어그램
      sequenceDiagram
    participant B as 브라우저 (사용자)
    participant S as 내 백엔드 서버
    participant O as OAuth 인증 서버 (구글/카카오)

    Note over B,O: 1단계 인증
    B->>O: 1. ID / PW 전송 (HTTPS)
    Note right of O: 신원 검증, 동의 확인
    O-->>B: 2. 302 Redirect (callback?code=AUTH_CODE)

    Note over B,S: 2단계 코드 전달
    B->>S: 3. GET /callback?code=AUTH_CODE

    Note over S,O: 3단계 토큰 교환
    S->>O: 4. POST /token (code + Secret Key)
    Note right of O: code, Secret 검증
    O-->>S: 5. Access Token 응답

    Note over S: 4단계 자체 JWT<br/>사용자 정보 조회 & 회원가입<br/>자체 서비스용 JWT 발급

    Note over B,S: 5단계 정착
    S-->>B: 6. 최종 응답<br/>(A: Set-Cookie 에 JWT / B: JSON 본문에 JWT)

  9. Code Deploy
    • 배포 방식의 진화
      • 고전적인 Jenkins 배포 : 빌드 → 산출물 전송(scp / rsync) → SSH 로 접속해서 배포 명령 (push 방식)
        • Jenkins 서버가 대상 서버의 SSH 키(Credentials)를 들고 있다
        • 문제점 : 키 유출 위험, 서버가 많으면 느리고 버전이 어긋날 수 있음, 롤백을 직접 스크립트로
      • Ansible : 여러 서버에 같은 작업을 반복 (플레이북)
      • 컨테이너 / k8s / GitOps : 이미지를 배포 단위로, 서버가 가져가는 pull 방식
    • 여러대에 배포를 하려면 어떤 전략이 있을까
      • rolling, blue/green, canary
    • LoadBalancer, Health check
      • 좀 더 복잡한 구조일 때 효율적인 배포한번 봐보기
    • ansible 사용법 : 남이 작성한 것 플로우 따라가보기
    • 실제 2대 서버로 무중단으로 배포해보기
      • 마음대로 조작해보자
    • 시간남으면 k8s 배포해볼까
